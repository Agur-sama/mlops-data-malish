# Объяснение лабораторной работы №4

## 1. Цель работы

Цель — научиться воспроизводимо сравнивать ML-модели. Важно не просто получить
высокую метрику, а доказать, на какой версии данных, с какими параметрами и на
каком split она получена. MLflow хранит эксперименты, а ClearML регистрирует
лучшую проверенную модель.

## 2. Что сделано

1. `wine.csv` получается по ClearML Dataset ID и сразу проверяется SHA-256.
2. Данные один раз делятся на train/validation/test в пропорции 60/20/20 со
   стратификацией и seed 42.
3. Обучаются три Logistic Regression и три Random Forest.
4. Для каждого run пишутся параметры, одинаковые validation-метрики, время,
   теги данных, signature, пять входных строк и модель.
5. Runs извлекаются через `mlflow.search_runs` и сортируются по validation F1.
6. Только лучшая модель оценивается на test.
7. Лучшая модель повторно загружается из MLflow, а совпадение предсказаний и
   полнота логирования фиксируются в `verification.json`.
8. `publish_clearml.py` создаёт Task и публикует OutputModel.

Параметры выбраны в широком диапазоне сложности. Logistic Regression с
`C=0.0001` слишком сильно регуляризована, а Random Forest с одним деревом
глубины 1 слишком проста — это наглядные примеры недообучения. По мере роста
сложности F1 увеличивается, и лучшая конфигурация определяется однозначно.

## 3. Инструменты

- **Poetry** фиксирует прямые и транзитивные версии в `poetry.lock`.
- **ClearML Dataset** даёт неизменяемый ID версии данных и lineage.
- **MLflow** хранит runs, параметры, метрики, модель и артефакты.
- **scikit-learn Pipeline** объединяет preprocessing и классификатор, поэтому
  при инференсе нельзя забыть StandardScaler.
- **pytest** проверяет хэш, split и набор конфигураций до дорогого запуска.

## 4. Как работает реализация

`run_experiments.py` сначала вызывает `resolve_wine_csv`, затем
`load_verified_data`. Несовпадение хэша останавливает процесс до обучения.
`make_split` создаёт общий split. `experiment_configurations` возвращает ровно
шесть содержательно разных конфигураций. Тег `invocation_id` отделяет runs
текущего запуска от предыдущих повторов. Лучший run выбирается по
`metrics.f1_weighted`; test-метрики записываются только в него.

`publish_clearml.py` читает уже проверенные артефакты, создаёт новый Task,
прикрепляет таблицу сравнения и регистрирует `best_model.joblib` как
OutputModel. В metadata модели записываются MLflow run ID, Dataset ID и SHA.

## 5. Как запустить

```bash
poetry install --with test --no-root
poetry run pytest -q
poetry run python run_experiments.py \
  --dataset-id "$WINE_ID" --expected-sha256 "$WINE_SHA256"
poetry run python publish_clearml.py
poetry run mlflow ui --backend-store-uri ./mlruns --port 5000
```

## 6. Как проверить

В MLflow должно быть шесть runs с одинаковыми dataset-тегами и split. У всех
есть validation-метрики и model artifact. Только у лучшего есть `test_*`.
`artifacts/verification.json` должен содержать четыре значения `true`.
В ClearML Task должны быть comparison, verification и test-метрики, а Model
должна иметь статус Published.

## 7. Что показать на защите

1. `poetry run pytest -q`.
2. Команду запуска с Dataset ID и SHA.
3. Таблицу runs в MLflow и сортировку по validation F1.
4. Внутри лучшего run: params, tags, metrics, signature и artifacts.
5. `verification.json`.
6. ClearML Task и опубликованную модель с metadata.

## 8. Возможные вопросы преподавателя

1. **Почему нельзя выбирать модель по test?** Test имитирует неизвестные данные;
   подбор по нему приводит к переобучению на test.
2. **Зачем validation?** На ней сравниваются конфигурации до финальной оценки.
3. **Зачем проверять SHA-256?** Dataset ID без проверки файла не доказывает,
   что обучение шло на ожидаемых байтах.
4. **Почему нужен Pipeline?** Он сохраняет preprocessing вместе с моделью.
5. **Что такое signature?** Описание входной и выходной схемы модели.
6. **Почему у всех runs один split?** Иначе метрики сравнивали бы разные задачи.
7. **Зачем `invocation_id`?** Повторный запуск добавляет runs в тот же experiment;
   тег позволяет выбирать лучшую модель только среди текущих шести.
8. **Чем MLflow отличается от ClearML здесь?** MLflow сравнивает локальные runs,
   ClearML связывает лучшую модель с централизованным Dataset и Task.
9. **Что произойдёт при неверном хэше?** Скрипт завершится с ненулевым кодом до
   создания runs.
10. **Почему Logistic Regression может победить Random Forest?** Wine хорошо
    разделяется после стандартизации; более сложная модель не всегда лучше.
11. **Почему метрики теперь сильно различаются?** Все модели видят один split,
    но имеют разную мощность. Слабые настройки добавлены не для искусственного
    ухудшения результата, а чтобы показать влияние регуляризации, глубины и
    числа деревьев; сравнение остаётся честным.
