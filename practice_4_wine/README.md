# Практика №4. Управление экспериментами на Wine

## О чём эта работа

В этой практике я сравнил шесть вариантов моделей классификации на датасете Wine: три настройки Logistic Regression и три настройки Random Forest. Задача была не просто получить высокую точность, а сделать сравнение воспроизводимым: использовать одни данные и одно разбиение, сохранить параметры и метрики каждого запуска, а затем выбрать модель по понятному правилу.

Для этого использовал **ClearML** как источник зафиксированной версии датасета и место публикации готовой модели, а **MLflow** — для истории экспериментов. Библиотека scikit-learn отвечает за подготовку признаков и обучение, Poetry — за зависимости, pytest — за проверки.

## Данные и подготовка

Используется Wine Dataset из третьей практики. В ClearML он хранится в наборе `sklearn-tabular-malish` версии `1.1.0`; внутри находятся `iris.csv` и `wine.csv`. В файле Wine — **178 объектов**, 13 числовых признаков и столбец с классом.

- [Датасет в ClearML](https://app.clear.ml/datasets/simple/7735890b414747d493153662254d5051/experiments/9a2b28de618840fc89baf3d5daf64b20)
- Dataset ID: `9a2b28de618840fc89baf3d5daf64b20`
- SHA-256 файла `wine.csv`: `38860ba04ace4d402242340bcf40be4bd6f4ebde9144a3dc89dc12c20f7f8e60`

Скрипт сначала получает датасет по ID, затем сверяет хэш CSV с ожидаемым. Если файл не найден или хэш отличается, обучение не начинается. Проверка сохраняется в `artifacts/dataset_verification.json`.

Для всех шести моделей используется одно стратифицированное разбиение при `random_state=42`: **106 объектов на train, 36 на validation и 36 на test** (примерно 60/20/20). Состав выборок записан в `artifacts/split_manifest.csv`. На test смотрю только после того, как выбрана лучшая модель по validation, иначе оценка получится необъективной.

## Как устроено обучение

Основная программа — `run_experiments.py`. Она загружает и проверяет данные, формирует общий split и последовательно обучает шесть конфигураций. Для моделей, которым необходима стандартизация, подготовка признаков входит в scikit-learn Pipeline вместе с классификатором. Это важно: при повторном использовании модели преобразование признаков не потеряется.

Каждый запуск MLflow сохраняет параметры, validation-метрики, время обучения, идентификаторы данных, пример входных значений, signature и саму модель. Тег `invocation_id` помогает отделить шесть запусков одного выполнения скрипта от результатов предыдущих повторов.

Для выбора использую **weighted F1 на validation**: чем выше значение, тем лучше. После выбора победителя скрипт один раз рассчитывает test-метрики, загружает сохранённую модель обратно из MLflow и проверяет совпадение предсказаний. Итоги этих проверок находятся в `artifacts/verification.json`.

## Полученные результаты

Все конфигурации обучались на одних и тех же данных. Я специально взял широкий диапазон сложности, включая очень простые модели, чтобы было видно, как гиперпараметры влияют на качество.

| Модель | Настройка | Weighted F1 на validation |
|---|---|---:|
| Logistic Regression | `C=0.0001` | 0.217778 |
| Random Forest | 1 дерево, глубина 1, `min_samples_leaf=10` | 0.464646 |
| Logistic Regression | `C=0.001` | 0.725530 |
| Random Forest | 3 дерева, глубина 2, `min_samples_leaf=5` | 0.944269 |
| Logistic Regression | `C=0.002` | 0.944961 |
| **Random Forest** | **10 деревьев, глубина 3, `min_samples_leaf=3`** | **0.972263** |

Слабые варианты заметно недообучаются: например, дерево глубины 1 не может выделить достаточно сложные зависимости. У логистической регрессии слишком маленькое `C` означает сильную регуляризацию. При этом усложнение модели не гарантирует улучшение на любых данных — именно поэтому сравнение проводилось на общей validation-выборке.

Победитель — **Random Forest с 10 деревьями, `max_depth=3` и `min_samples_leaf=3`**.

Итог на отложенной test-выборке:

| Метрика | Значение |
|---|---:|
| Accuracy | 0.972222 |
| Precision weighted | 0.975000 |
| Recall weighted | 0.972222 |
| F1 weighted | **0.972474** |

Test-метрики сохранены **только для победившего запуска**. Модель повторно загружалась из MLflow; её предсказания до и после сохранения совпали.

## Как запустить

Рабочая папка — `practice_4_wine`. Для установки нужен **Python 3.12**, Poetry и настроенный доступ к ClearML. В исходном запуске использовались Python 3.12.5, MLflow 2.19.0, ClearML SDK 1.16.5 и scikit-learn 1.5.2; версии зависимостей зафиксированы в `poetry.lock`. Учётные данные ClearML следует хранить в `~/clearml.conf` или переменных окружения, но не в репозитории.

Из корня Git-репозитория:

```bash
cd practice_4_wine
poetry install --with test --no-root
poetry run pytest -q
```

Чтобы посмотреть **уже сохранённые** официальные эксперименты, переобучать модели не требуется:

```bash
poetry run mlflow ui --backend-store-uri ./mlruns --host 127.0.0.1 --port 5000
```

Открой <http://127.0.0.1:5000> и выбери эксперимент `miit-mlops-practice-4-malish`. В нём должны быть шесть runs с разными F1. Можно открыть лучший run и показать вкладки Params, Metrics, Tags и Artifacts, включая signature. Если порт занят прежним MLflow, укажи `--port 5001` и открой <http://127.0.0.1:5001>.

Чтобы **повторно запустить обучение** на официальном датасете (это создаст ещё шесть runs):

```bash
poetry run python run_experiments.py \
  --dataset-id 9a2b28de618840fc89baf3d5daf64b20 \
  --expected-sha256 38860ba04ace4d402242340bcf40be4bd6f4ebde9144a3dc89dc12c20f7f8e60 \
  --tracking-uri file:./mlruns
```

Для публикации модели в ClearML:

```bash
poetry run python publish_clearml.py --project MIIT/MLOps/practice_4/malish
```

Последняя команда создаёт **новую** Task и запись модели. Если нужно только показать готовую практику, запускать её повторно не надо — достаточно перейти по ссылке выше.

Для проверки кода без ClearML существует параметр `--wine-csv`. Это лишь предварительный локальный тест, он отмечается `local-preflight:*` и не заменяет официальный эксперимент.

## Что находится в папке

- `run_experiments.py` — получение данных, разбиение, обучение, MLflow и проверка сохранённой модели.
- `publish_clearml.py` — публикация выбранной модели и её происхождения в ClearML.
- `tests/` — проверки данных, split и настроек эксперимента.
- `pyproject.toml` и `poetry.lock` — зависимости и их версии.
- `mlruns/` — сохранённые эксперименты MLflow. Небольшие служебные файлы внутри — часть базы MLflow, удалять их нельзя.
- `artifacts/comparison.csv` — итоговое сравнение шести запусков.
- `artifacts/split_manifest.csv` — состав train/validation/test.
- `artifacts/dataset_verification.json` и `artifacts/verification.json` — проверка данных и модели.
- `artifacts/summary.json`, `best_model.joblib`, `classification_report.json` и `confusion_matrix.csv` — итоговые сведения, модель и дополнительные результаты.

## Что показать на защите

Сначала я бы показал источник Wine Dataset в ClearML и проверку SHA-256. Затем открыл бы MLflow, где видны шесть запусков с одним split, но разными настройками моделей. По столбцу weighted F1 на validation видно, почему выбран Random Forest. После этого можно открыть лучший run, показать отдельные test-метрики и `verification.json`, а в конце перейти в ClearML Task с опубликованной моделью.

**Короткое объяснение:** «Я сравнил шесть конфигураций на одной версии Wine Dataset. Все обучались на одинаковом разбиении, поэтому метрики сопоставимы. Лучший вариант выбрал по validation F1, а test использовал только для окончательной оценки. MLflow сохранил историю экспериментов и модель, а ClearML связал опубликованную модель с исходными данными и конкретным запуском».

Полезно помнить несколько отличий:

- **Почему не выбирал по test?** Иначе test перестаёт быть независимой оценкой.
- **Зачем SHA-256?** Чтобы убедиться, что получен именно тот CSV, с которым проводились эксперименты.
- **Зачем scikit-learn Pipeline?** Чтобы преобразование признаков применялось одинаково при обучении и при использовании модели.
- **Что такое MLflow signature?** Описание формата входных и выходных данных модели.
- **Зачем `invocation_id`?** Чтобы при повторном обучении не смешать новые runs со старыми.
- **Чем MLflow отличается от ClearML в этой работе?** В MLflow сравниваются эксперименты, а через ClearML берётся зафиксированный датасет и публикуется выбранная модель.

Все основные результаты уже сохранены в `mlruns/` и `artifacts/`. Для демонстрации достаточно запустить тесты и MLflow UI, не создавая новые эксперименты.
